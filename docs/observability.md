# Observability

What the lab watches, what it deliberately does not, and how to change
either. The manifests are the source of truth — every file named here
carries its own "why" header, and this document is the map between them
plus the operational procedures that live in no single file.

Scope: metrics, logs and alerting for the Proxmox host, the k3s VM, the
cluster and the media stack. Everything runs inside the one k3s node and
alerts out to a Telegram group. There is nothing watching from outside the
lab — see [Deliberately not monitored](#deliberately-not-monitored).

## The component map

Four Argo `Application`s, one `monitoring` namespace, one config overlay:

| File | Wave | What it is |
|---|---|---|
| [`kube-prometheus-stack.yaml`](../clusters/lab/platform/kube-prometheus-stack.yaml) | `"4"` | Prometheus + the prometheus-operator CRDs, Alertmanager, Grafana, kube-state-metrics, node-exporter |
| [`loki.yaml`](../clusters/lab/platform/loki.yaml) | `"4"` | Loki, single-binary, filesystem storage, ruler enabled |
| [`alloy.yaml`](../clusters/lab/platform/alloy.yaml) | `"5"` | Grafana Alloy DaemonSet — pod logs + the host journal into Loki |
| [`monitoring-config.yaml`](../clusters/lab/platform/monitoring-config.yaml) | `"5"` | git-source app → [`monitoring/`](../clusters/lab/platform/monitoring/), everything that is a plain Kubernetes object |

That bends this repo's usual component layout, which is one chart app + one
config app + one overlay per component
([`clusters/lab/platform/README.md`](../clusters/lab/platform/README.md)).
Three charts share **one** overlay because the objects in it are not
separable by chart: a `PrometheusRule` about ZFS pools is written against
the *pve-exporter's* metrics, evaluated by *Prometheus*, and routed by an
Alertmanager config written for the alerts the rules define. Splitting them
into three overlays would put a sync-ordering edge between files that always
change together, for no gain.

Two consequences worth stating because both are easy to "tidy up" into a
bug:

- **`CreateNamespace=true` lives on `kube-prometheus-stack.yaml` alone.** It
  is the wave-4 Application that gets to the namespace first. Repeating it
  on `loki.yaml` or `alloy.yaml` would leave two Applications claiming the
  same namespace object.
- **Waves 4–5 sit strictly after `apps.yaml` (wave 3).** Monitoring scrapes
  everything and nothing depends on monitoring, so it is last in and first
  out. `monitoring-config.yaml` trails the charts by a wave because its CRs
  need the kube-prometheus-stack CRDs established first.

The two `.sops.yaml` files are **operator-created and never generated by a
tool**; each has a committed `.sops.yaml.example` beside it showing the
shape. Every filename listed in `secret-generator.yaml` must exist in git or
the whole overlay fails to render — ksops has no `optional:`.

## What gets scraped

Nothing here is discovered by accident; each target is either a chart's own
ServiceMonitor or a hand-written CR.

- **The cluster** — kubelet, kube-apiserver and CoreDNS via the chart's own
  ServiceMonitors, plus kube-state-metrics and the node-exporter DaemonSet.
  `kubeEtcd`, `kubeScheduler`, `kubeControllerManager` and `kubeProxy` are
  switched off in both halves (Services *and* rules): k3s has no etcd and
  folds those three components into the server process with no separately
  scrapeable ports, so the targets would be permanently down and the
  matching alerts permanently firing.
- **The stack itself** — Loki and Alloy render their own ServiceMonitors
  (`monitoring.serviceMonitor.enabled` / `serviceMonitor.enabled`). Loki's
  is gated on the ServiceMonitor CRD existing, so it does not appear in
  CI's bare `helm template` output; it appears in the live cluster, where
  the CRD is already established.
- **The hypervisor** — two targets, one layer below Kubernetes:
  `job="pve-exporter"` (the PVE API: guests, storages, quorum) and
  `job="pve-node"` (the host's own node_exporter on `10.10.10.1:9100`, over
  the vmbr1 bridge).
- **The media stack** — five targets in the **`media`** namespace, the only
  scraped workloads outside `monitoring`. Three exportarr containers
  ([`apps/exportarr.yaml`](../clusters/lab/apps/exportarr.yaml)) as
  `job="exportarr-sonarr"`, `job="exportarr-radarr"` and
  `job="exportarr-prowlarr"`; the Plex exporter
  ([`apps/plex-exporter.yaml`](../clusters/lab/apps/plex-exporter.yaml)) as
  `job="plex-exporter"`; and a Deluge exporter sidecar inside the Deluge pod
  ([`apps/deluge.yaml`](../clusters/lab/apps/deluge.yaml)) as `job="deluge"`.
  All five ServiceMonitors are chart-rendered, so the selector and the port
  name cannot drift from the Service they point at.

  The three exportarr jobs are only distinguishable because their
  ServiceMonitors set **`jobLabel: app.kubernetes.io/service`**. The chart's
  default `jobLabel` is `app.kubernetes.io/name`, which is the *release* name
  — `exportarr` on all three Services — and would collapse the three targets
  into one job, making `up{job="exportarr"}` unable to say which exporter is
  down. Deluge and the Plex exporter keep the default: one Service each,
  nothing to collapse.

A standalone `ServiceMonitor`, `PodMonitor`, `Probe`, `PrometheusRule` or
`ScrapeConfig` is picked up **with no `release` label and in any namespace**,
because all five `*SelectorNilUsesHelmValues` are `false` and the rendered
Prometheus CR therefore carries `serviceMonitorSelector: {}`,
`ruleSelector: {}`, `scrapeConfigSelector: {}` and the rest. Adding a
`release: kube-prometheus-stack` label would imply a coupling that does not
exist.

The namespace selectors matter and they are easy to get backwards. In
prometheus-operator terms an **empty** label selector (`{}`) matches *all*
namespaces, while a **null** one — the field absent, which is the CRD default
— matches the Prometheus object's own namespace only:

> `serviceMonitorNamespaceSelector` defines the namespaces to match for
> ServicedMonitors discovery. An empty label selector matches all namespaces.
> A null label selector (default value) matches the current namespace only.
>
> — `pkg/apis/monitoring/v1/prometheus_types.go` at operator `v0.92.1`, the
> `appVersion` of chart 87.21.0

The rendered CR carries the **empty** form on all five pairs, so discovery is
cluster-wide. That is what lets the media stack's five ServiceMonitors live
in `media`, chart-rendered beside the workloads they scrape, instead of being
hand-copied into `monitoring`. Adding a label-matching
`serviceMonitorNamespaceSelector` to "tighten" this would silently drop every
media target: the targets vanish, no alert fires about their absence, and
only `TargetDown` on the ones that remain would hint at it.

### The two job labels are a contract

`job="pve-node"` and `job="pve-exporter"` are load-bearing strings shared
between the CR that creates the target and every rule that selects on it.
The in-cluster node-exporter DaemonSet emits series with **identical names**
to the hypervisor's (`node_filesystem_avail_bytes`,
`node_cpu_seconds_total`, …), so a rule that forgets the matcher fires a
hypervisor alert for a VM-level condition — or, worse, silently mixes the
two sets of series, which are indistinguishable by metric name alone. Every
rule in `rules-pve-host.yaml` carries it.

## Sizing and retention

| Component | PVC | Retention | Requests | Limits |
|---|---|---|---|---|
| Prometheus | 15 Gi | 15 d **or** 13 GiB, whichever comes first | 200m / 1 Gi | 1 CPU / 2 Gi |
| Alertmanager | 1 Gi | — | 10m / 64 Mi | — / 128 Mi |
| Loki | 10 Gi | 720 h (30 d), compactor-enforced | 100m / 512 Mi | — / 1 Gi |
| Grafana | **none** | — | 50m / 256 Mi | — / 512 Mi |
| Alloy (DaemonSet) | none | — | 50m / 128 Mi | — / 256 Mi |
| prometheus-operator | none | — | 50m / 128 Mi | — / 256 Mi |
| kube-state-metrics | none | — | 10m / 128 Mi | — / 256 Mi |
| node-exporter | none | — | 10m / 32 Mi | — / 64 Mi |
| pve-exporter | none | — | 25m / 64 Mi | — / 256 Mi |

Roughly 2.3 GiB of memory requested in total, against the VM's 32 GiB, and
26 Gi of PVC.

Three notes on the numbers:

- Prometheus's `retentionSize: 13GiB` is **not** the PVC size. The 2 GiB of
  head-room is for the WAL and for compaction's transient double-write; set
  them equal and the disk fills before the size-based retention ever trips.
- Grafana has **no PVC on purpose**. Dashboards are provisioned from git, so
  the only thing a restart loses is an unsaved ad-hoc panel. Nothing worth
  keeping should ever be created in Grafana's own UI.
- Loki's `retention_period` on its own only *marks* data expired. The
  deletion is the compactor's job, which is why `compactor.retention_enabled`
  is set as well — without it nothing ever removes a chunk and the PVC fills
  regardless of the period.

## Where a PVC actually lives

**None of the three land on the 64 GB OS disk**, and since Phase 8 none of
them land on the 150 GB data disk either. `k3s-node` has three disks, and the
monitoring PVCs are the reason the third one exists:

| Disk | Size | Mounted at | In the VM backup? | Holds |
|---|---|---|---|---|
| `scsi0` | 64 GB | `/` | yes | the OS |
| `scsi1` | 150 GB | `/var/lib/rancher/k3s/storage` | yes | every PVC on the default `local-path` class — Plex metadata, the \*arr DBs |
| `scsi2` | 40 GB | `/var/lib/rancher/k3s/ephemeral` | **no** (`backup = false`) | the Prometheus, Alertmanager and Loki PVCs, via `local-path-ephemeral` |

The split is a backup decision, not a capacity one. `vzdump` of VM 9000 is
block-level and cannot exclude a path, so the only way to keep ~25 GB of
daily-churning TSDB out of the PBS datastore — and out of B2 for the six
months `keep-monthly` would hold those chunks — is to put it on a disk the
backup job never reads. [`docs/backups.md`](backups.md) carries the full
picture, including what else is excluded and why.

The chain, end to end:

1. [`infra/tofu/vm-k3s.tf`](../infra/tofu/vm-k3s.tf) attaches the three disks
   above, sized by `var.vm_disk_size_gb` (**64**), `var.vm_data_disk_size_gb`
   (**150**) and `var.vm_ephemeral_disk_size_gb` (**40**). Only `scsi2`
   carries `backup = false`.
2. [`ansible/roles/k3s/tasks/disk.yml`](../ansible/roles/k3s/tasks/disk.yml)
   formats both data disks `ext4` and mounts them, at `k3s_storage_mount_path`
   and `k3s_ephemeral_mount_path` respectively, **before** k3s's first start.
3. `/var/lib/rancher/k3s/storage` is the bundled local-path-provisioner's
   default directory, so the default StorageClass resolves to `scsi1` from
   the very first PV. `/var/lib/rancher/k3s/ephemeral` is the `nodePathMap` of
   the second provisioner in
   [`clusters/lab/platform/local-path-ephemeral/`](../clusters/lab/platform/local-path-ephemeral/),
   which serves the non-default `local-path-ephemeral` StorageClass named
   explicitly by `kube-prometheus-stack.yaml` and `loki.yaml`.

`local-path` remains the cluster default, so anything that omits
`storageClassName` lands on the backed-up disk. Opting *out* of backup is
always an explicit line in a manifest.

**To grow either, raise the matching Tofu variable, never `vm_disk_size_gb`**
— that one grows the OS disk and leaves every PV exactly as cramped as it
was. Two traps on the way:

- `roles/k3s` refuses to guess which block device is which. It auto-detects
  each by "not the root disk, and sized inside this disk's window" — **140 to
  170 GB** for the data disk, **30 to 50 GB** for the ephemeral one — and
  `disk.yml` asserts the two windows do not overlap before touching anything.
  Growing a disk out of its window makes the role's assert fail on the next
  run rather than mkfs the wrong device. Move the size and the window
  together, and keep the windows disjoint.
- Device letters are not stable on this VM's virtio-scsi controller — on the
  real machine `/dev/sdb` is the *root* disk and `/dev/sda` the data disk,
  the opposite of what a naive `scsi0=sda` reading predicts. Never hardcode
  a device.

To see what is actually consuming them, from `k3s-node`:

```sh
ssh debian@k3s.lab.tomkatom.com 'sudo sh -c "du -sh /var/lib/rancher/k3s/storage/* /var/lib/rancher/k3s/ephemeral/*"'
```

The `sudo sh -c` wrapper is required: an unprivileged login shell cannot
traverse those directories, so it never expands the glob and `du` is handed a
literal `*`.

## The alert catalog

Severities are `warning` and `critical` only; both go to the same Telegram
group. `for:` durations are as configured, not as suggested.

### Metric alerts — the hypervisor

From [`monitoring/rules-pve-host.yaml`](../clusters/lab/platform/monitoring/rules-pve-host.yaml),
group `pve-host`. Everything here selects `job="pve-node"` or
`job="pve-exporter"`.

| Alert | Sev | Fires when | First response |
|---|---|---|---|
| `PveNodeExporterDown` | critical | `up{job="pve-node"} == 0` for 5m | `systemctl status prometheus-node-exporter` on the host. Every other alert in this group is blind until it returns, so treat it first. |
| `PveZpoolNotOnline` | critical | the pool's `online` kstat is 0 for 5m | `zpool status -v <pool>` on the host; identify the failing vdev before touching anything. |
| `ZfsPoolCapacityHigh` | warning | pool over 80 % for 30m | `zfs list -t snapshot` — deleting files that a snapshot still pins frees nothing. |
| `ZfsPoolCapacityHigh` | critical | pool over 90 % for 10m | Same, urgently: past ~90 % ZFS switches to a slower allocator, and a pool at 100 % can refuse the very writes a delete needs. |
| `PveHostFilesystemFillingUp` | warning | a non-tmpfs, writable filesystem under 15 % free for 30m | `df -h` on the host. The alert names the mountpoint and device. |
| `SmartDeviceUnhealthy` | critical | `smartmon_device_smart_healthy == 0` for 5m | `smartctl -a /dev/<disk>`. Treat the drive as failing and check which pool it backs. Note a drive that stops answering SMART goes *quiet* rather than firing this. |
| `MediaBackupStale` | warning | newest Sonarr/Radarr backup older than 8 d, **or absent entirely**, for 1h | Check the *arr's Settings → General → Backup schedule, then that `/data/backups/<app>` on the VM is being written. |
| `PveGuestNotRunning` | critical | a non-template guest is not running for 10m | `qm status <id>` / the Proxmox UI. Everything this lab serves runs inside one of these. |

Two of these depend on metrics that exist nowhere upstream —
`zfs_pool_capacity_ratio{pool}` and `media_backup_newest_mtime_seconds{app}`
come from `ansible/roles/node_exporter`'s own textfile collector
(`templates/lab-node-metrics.sh.j2`). The label names are hand-copied from
that script into the rules and **nothing checks the two agree**: rename a
label there and these rules keep evaluating, keep matching nothing, and
never fire again. `MediaBackupStale`'s per-app `absent()` clauses are
hard-coded to that role's `node_exporter_backup_apps` list for the same
reason — adding an app there means adding a clause here.

### Metric alerts — backups

From [`monitoring/rules-backups.yaml`](../clusters/lab/platform/monitoring/rules-backups.yaml),
group `backups`. Every series these read comes from `ansible/roles/pbs`'
textfile collector (`templates/lab-backup-metrics.sh.j2`) through the same
`job="pve-node"` scrape as the hypervisor rules above — PBS has no Prometheus
endpoint at any version, it pushes to InfluxDB or Graphite and to nothing
else.

| Alert | Sev | Fires when | First response |
|---|---|---|---|
| `BackupStale` | critical | the newest complete snapshot for `host/server` or `vm/9000` is over 36 h old, **or there is none**, for 1h | Two consecutive nightly runs have failed. `systemctl status lab-host-backup` on the host for `host/server`; the vzdump task log in the Proxmox UI for `vm/9000`. |
| `PbsVerifyStale` | warning | no verify task has finished OK in 10 d, **or ever**, for 1h | `proxmox-backup-manager verify-job run lab-verify`, then read the task log. Until this clears, nothing has confirmed the chunks in B2 are still readable. |
| `PbsGcStale` | warning | no garbage collection has finished OK in 10 d, **or ever**, for 1h | `proxmox-backup-manager garbage-collection list`. Pruned snapshots keep costing B2 storage until GC runs. |
| `PbsDatastoreUnreachable` | critical | `lab_backup_datastore_reachable == 0` for 30m | `systemctl status proxmox-backup-proxy proxmox-backup`, then the credential and certificate fingerprint. Backups are failing *now*, not in 36 h. |
| `PbsCacheDiskHigh` | warning | the local chunk cache is over 85 % of its quota for 1h | `zfs list -o space rpool/pbs-cache`. PBS evicts from this cache itself, so a high reading means something else is filling the dataset. A full cache stops backups. |
| `RestoreDrillOverdue` | warning | the drill marker is over 180 d old, **or has never been written**, for 1h | Follow the restore runbook to the end; its last step touches the marker. |
| `BackupMetricsStale` | warning | `lab-backup.prom` has not been rewritten in over an hour, for 30m | `systemctl status lab-backup-metrics.service lab-backup-metrics.timer`. Every other alert in this group is reading frozen numbers until it clears. |

Two things about this group are easy to get wrong when adding to it:

- **`RestoreDrillOverdue` fires on a host where no drill has ever been run**,
  and that is deliberate. Ansible creates the marker's *directory* and never
  the marker — a seeded file would clear the alert by asserting a restore had
  been proven when none had. It is the one alert here that cannot be
  satisfied by a machine.
- **The cache metric is named for the cache, not the datastore.**
  `proxmox-backup-client status` against an S3-backed datastore reports the
  *local chunk cache filesystem* — its `total` is exactly the ZFS quota on
  `rpool/pbs-cache`. PBS does not expose how much sits in the B2 bucket at
  all, and no alert watches that; what is in B2 is bounded by the prune
  policy.

`lab_backup_*` follows `media_backup_newest_mtime_seconds`' absence rule
exactly — no series at all for a backup, verify, GC or drill that has never
happened, so every staleness rule above carries a paired `absent()` clause
naming each expected target. `host/server` and `vm/9000` are hard-coded from
`roles/pbs`' `pbs_host_backup_id` and `infra/tofu/backup.tf`'s `vmid`
respectively; adding a backup target means adding a clause.

### Metric alerts — the cluster

From [`monitoring/rules-cluster.yaml`](../clusters/lab/platform/monitoring/rules-cluster.yaml),
group `cluster-extra`. Deliberately small: it holds only what the chart has
no opinion about.

| Alert | Sev | Fires when | First response |
|---|---|---|---|
| `CertificateExpiringSoon` | warning | a cert-manager Certificate expires in under 21 d, for 1h | cert-manager renews at 30 days remaining, so this means renewal has been failing for over a week. `kubectl -n <ns> describe certificate <name>`, then the Order and Challenge objects beside it. |
| `CertificateNotReady` | warning | `Ready` condition `False` for 1h | Same investigation. The existing Secret may still be valid, so this is a warning until `CertificateExpiringSoon` joins it. |

The Certificate's real namespace is in the **`exported_namespace`** label,
not `namespace` — the ServiceMonitor relabeling overwrites `namespace` with
the scraped pod's, so on every one of these series `namespace` is
`cert-manager`. The annotations use the right one; anything you add should
too.

### Metric alerts — the media stack

From [`monitoring/rules-media.yaml`](../clusters/lab/platform/monitoring/rules-media.yaml),
group `media`. These read the five `media`-namespace exporters above; nothing
in kube-prometheus-stack knows these applications exist.

| Alert | Sev | Fires when | First response |
|---|---|---|---|
| `ArrHealthErrors` | warning | a Sonarr/Radarr/Prowlarr health issue at `type="error"` for 1h | The alert carries Servarr's own `message`. Open the app's System → Status page. This is also the closest thing to a blocked-import alert the stack has — broken remote path mappings, unavailable download clients and missing root folders all surface here. |
| `ProwlarrIndexerUnhealthy` | warning | `prowlarr_indexer_unavailable > 0` for 6h | Every *arr search runs through Prowlarr, so a dead indexer is silently missing releases rather than raising an error. Check the indexer's own status page and Prowlarr's History. A healthy Prowlarr emits **no series at all** for this rule — that is normal, not a fault. |
| `PlexDown` | critical | `plex_up == 0` for 5m | The exporter's call to Plex's `/identity` failed. This means Plex, not the exporter: a bad `PLEX_TOKEN` or a dead exporter pod fails the *scrape* instead, which the chart's `TargetDown` already covers. |
| `PlexVideoTranscodeSession` | warning | any video-transcoding session for 15m | There is no GPU in an E5-1650v4, so this is software libx264 on the cores the *arrs and Deluge are using. Find the file and the client in Tautulli and decide which of the two is outside the direct-play policy. Audio-only transcodes are cheap and deliberately not alerted on. |
| `DelugeDown` | critical | `absent(deluge_info)` for 5m | ⚠ **The scrape can still be succeeding** — this exporter returns HTTP 200 with a near-empty body when its RPC connection fails, so `up == 1` for a completely dead daemon and `deluge_up` does not exist. Run `kubectl -n media logs deploy/deluge -c metrics` before assuming the pod is down. While it fires, nothing is seeding and no *arr grab completes. |
| `DelugeTorrentsInError` | warning | `deluge_torrents{state="error"} > 0` for 30m | Today this is 0 of ~390 torrents, so any error state is signal rather than noise. Usual causes: a missing path under `/data/torrents`, or a tracker that has stopped accepting announces. State values are lowercase — `state="Error"` matches nothing. |

> ⚠ **There is deliberately no queue-state alert, and adding the obvious one
> would be worse than the gap.** At the pinned exportarr **v2.3.0** the queue
> collector emits a single `<app>_queue_total` series per scrape — it assigns
> to one `prometheus.Metric` variable inside the loop over queue records and
> sends only the last (`internal/arr/collector/queue.go:88-96` at that tag).
> The surviving series holds the *total* queue length under whichever
> record's labels came last, so
> `{__name__=~"(sonarr|radarr)_queue_total", download_state="importBlocked"}`
> fires on a coin flip and misreports the count when it does. The per-state
> grouping fix exists only on the exporter's unreleased `main`
> (upstream #389). `rules-media.yaml`'s header carries the rule to restore
> once a release later than v2.3.0 ships it. Until then the queue is watched
> on the **"*arr — queue size"** panel of the Media stack dashboard, where a
> queue that never drains is a line that never comes down.
>
> `ENABLE_UNKNOWN_QUEUE_ITEMS: "true"` on the sonarr and radarr exporters is
> what makes even that number honest: the *arr queue API hides items it
> cannot match to a series or movie by default, and that is very often
> *why* an item is stuck. It is set today and must stay set — a restored
> per-state rule without it would evaluate forever against a filtered view
> and read as a passing check.

> ⚠ **The three log thresholds — 10, 0 and 50 — are guesses.** Nothing had a
> week of log baseline to calibrate against when they were written. Paste

> over real traffic, and move it. `MediaAppErrorBurst` in particular will
> need moving, because "error" means something different in every
> application in that namespace.

### What the chart already covers

kube-prometheus-stack 87.21.0 renders **30 `PrometheusRule` objects
containing 120 distinct alerts** (etcd, scheduler, controller-manager and
kube-proxy rules excluded, since those components do not exist here). Among
them: `KubePodCrashLooping`, `KubePersistentVolumeFillingUp` (3 % and 15 %,
with a four-day linear prediction), `NodeFilesystemSpaceFillingUp`,
`NodeFilesystemAlmostOutOfSpace`, `TargetDown`, and the `Watchdog`
heartbeat.

**Do not restate any of them in `monitoring/`.** Two rules for one event,
with slightly different thresholds and no way to tell which is
authoritative, is worse than either alone. The hand-written files exist for
what the chart cannot see: the hypervisor, cert-manager, and logs.

One trap in the other direction: every upstream node-exporter rule is scoped
`job="node-exporter"`, so **none of them apply to the hypervisor**, whose
node_exporter is `job="pve-node"`. Without `rules-pve-host.yaml` the host
would be scraped, graphed, and never alert.

## How a notification reaches Telegram

`Prometheus (or the Loki ruler) → Alertmanager → Telegram Bot API → the
group`.

The whole Alertmanager configuration lives in the `alertmanager-config`
Secret, not in the chart's `alertmanager.config` values block, for two
reasons that only both hold this way: the bot token is a credential and
cannot sit in a committed `valuesObject`, and `chat_id` must be a bare
negative integer, which this repo's "every SOPS value is a quoted string"
rule would forbid — except that the rule binds the *outer* `alertmanager.yaml`
value (a block scalar, which is a string) and says nothing about the YAML
nested inside it.

Pointing the CR at that Secret takes **two** values, not one:
`configSecret: alertmanager-config` sets the CR field, while
`useExistingSecret: true` is what stops the chart from rendering its own,
unread, default-config Secret alongside it.

The routing, from the same file:

- Root receiver is `telegram`; anything not explicitly caught is delivered.
- `group_by: [alertname, namespace]`, `group_wait: 30s`,
  `group_interval: 5m`, `repeat_interval: 12h` — long enough that a
  known-unfixed alert is not noise, short enough to still nag.
- `Watchdog` and `InfoInhibitor` are routed to a `null` receiver. Both are
  synthetic alerts that fire permanently by design; without this they would
  message every 12 h forever. `InfoInhibitor` carries `severity: none`, so
  no severity-based rule catches it by accident — it has to be named.
- Three inhibit rules restate the chart's defaults (critical suppresses
  warning/info, warning suppresses info, `InfoInhibitor` suppresses info).
  Hand-writing the config replaces the chart's defaults wholesale, so
  dropping one of these is a silent noise regression rather than an error.
  The critical/warning pair is also what stops `ZfsPoolCapacityHigh` — one
  alertname at two severities — from sending two messages for one full pool.

The receiver runs with **`parse_mode: HTML`**, and that has one consequence
for every rule anyone writes: Alertmanager's default template prints each
annotation verbatim, so a stray `<` in a summary or description makes the
whole notification fail to send. Keep angle brackets out of annotations.

## How log-based alerting works

```
pods + journal ──Alloy──▶ Loki ──ruler──▶ Alertmanager ──▶ Telegram
```

Alloy runs as a DaemonSet and tails two sources: container logs (through the
Kubernetes API, not by tailing `/var/log/pods`) and the host's systemd
journal at `/var/log/journal`. The journal is not a nice-to-have: a
crash-looping k3s server, an OOM kill, a node reboot — none of that appears
in any pod's logs, because the thing that writes them has stopped.

Loki's ruler evaluates LogQL alerting rules in-process and posts to
`http://alertmanager-operated.monitoring.svc:9093`, the headless Service the
prometheus-operator creates for the Alertmanager CR. Rules come from the
`loki-rules` ConfigMap, mounted at **`/rules/fake`** — `fake` is the tenant
directory Loki attributes every request to when `auth_enabled: false`, not a
placeholder. Mount it at `/rules` instead and the ruler finds a directory
where it expects a tenant folder and loads zero rules, silently.

**The label set available to a LogQL selector is defined entirely by Alloy's
relabel rules**, and a selector naming a label nothing sets matches zero
streams forever with no error:

| Source | Labels |
|---|---|
| pod logs | `namespace`, `pod`, `container`, `app` — **no `job` label** |
| journal | `job="systemd-journal"`, `host="k3s-node"` — no namespace, no pod |

`app` comes from `app.kubernetes.io/name`, falling back to the legacy `app`
pod label.

## The four dashboards

Grafana carries 29. Twenty-five of them arrive with kube-prometheus-stack
(count them in a render: `grep -c 'grafana_dashboard: "1"'`) and are the
upstream Kubernetes mixin — written for large multi-tenant clusters, so on a
single-node lab a namespace picker and a per-workload CPU breakdown are
mostly noise. They are left enabled because they cost nothing and are
occasionally the fastest way to a pod-level number, but they are not the
ones to open first.

The four this repo writes are:

| Dashboard | uid | Question it answers |
|---|---|---|
| **Lab overview** | `lab-overview` | Is the lab OK *right now*? |
| **Media stack** | `lab-media-stack` | What have the *arrs, Plex and Deluge been doing? |
| **Backups** | `lab-backups` | Is there a recent, verified, restorable copy of this machine? |
| **Node Exporter Full** | `rYdddlPWk` | What is the host or the VM doing, in detail? |

**Lab overview is the home dashboard**, and it is meant to be the whole
answer: ten stat/bar-gauge tiles, no timeseries, no scrolling. If nothing on
it is amber or red, stop reading. Every threshold on it is deliberately the
threshold of the alert covering the same condition — 0.80/0.90 from
`ZfsPoolCapacityHigh`, 85% used from `PveHostFilesystemFillingUp`'s 15%-free,
21 days from `CertificateExpiringSoon`, 8 days from `MediaBackupStale` — so
amber on the board and a Telegram message are the same event, not two
opinions. Changing one without the other is how a dashboard starts
disagreeing with the alerts.

Two things about it are load-bearing and easy to break by tidying:

- **Its ConfigMap data key must stay `lab-overview.json`.** The dashboard
  sidecar runs with `FOLDER=/tmp/dashboards` and no `UNIQUE_FILENAMES`, so it
  writes each data key out as a file of that exact name in one flat
  directory. `kube-prometheus-stack.yaml` sets
  `dashboards.default_home_dashboard_path` to the resulting
  `/tmp/dashboards/lab-overview.json`. That path is a *file path inside the
  pod*, not a uid or a title. Rename the key — or change the sidecar's
  `FOLDER` — and Grafana silently falls back to its built-in home dashboard
  with no error anywhere. The key must also stay unique across every
  dashboard ConfigMap in the cluster, since the directory is flat.
- **The "*arr backups" tile counts apps, it does not show an age.** The
  textfile collector emits no series at all for an app with zero backups —
  deliberately, for the reason `MediaBackupStale` records in
  [Metric alerts — the hypervisor](#metric-alerts--the-hypervisor) — so an
  age panel would read "No data" for the case it exists to catch, or, with a
  naive `or vector(0)`, a perfectly fresh zero. A count treats absence as
  absence and the tile goes red on its own. The `of 2` is the role's
  `node_exporter_backup_apps`; adding an app there means bumping the tile's
  green threshold, exactly as it means adding an `absent()` clause to
  `MediaBackupStale`.

## Querying from the command line

Grafana is the exploratory surface, but it is behind Authelia and its session
is a browser. For a one-shot question — triaging an alert, checking whether a
metric exists before writing a rule against it, reading the logs of a pod that
has already been replaced — two read-only scripts query the stores directly:

```bash
scripts/promql.sh 'zfs_pool_capacity_ratio{job="pve-node"}'
scripts/promql.sh --since 6h --step 5m 'rate(node_cpu_seconds_total[5m])'
scripts/promql.sh --alerts      # firing now    --targets   # scrape health
scripts/promql.sh --rules       # rule group health

scripts/logql.sh '{namespace="media", app="sonarr"} |= "error"'
scripts/logql.sh --since 7d --limit 500 '{job="systemd-journal"} |= "oom"'
scripts/logql.sh --labels       # discover label names
scripts/logql.sh --values namespace
scripts/logql.sh --rules        # Loki ruler group health
```

**Neither script holds a credential**, and that is the point: Prometheus and
Loki have no authentication of their own, so the only problem to solve is
reachability. Both reach the stores through the **API server's service proxy**
(`kubectl get --raw /api/v1/namespaces/monitoring/services/<svc>/proxy/...`)
over `ssh k3s`, which is stateless and assumes neither host-side cluster DNS
nor host routing to a ClusterIP — the two things that make `curl` to a
ClusterIP and `kubectl port-forward` respectively awkward from an operator
shell. Authorization is therefore whatever the SSH user's kubeconfig already
grants; nothing new is issued.

The Service names are derived from the Helm release names, not observed live,
so a chart bump that renames them breaks the scripts. That failure is loud —
both print the namespace's Services and the `LAB_PROM_SVC` / `LAB_LOKI_SVC`
override to use.

`.claude/skills/lab-diagnose/` carries the same vocabulary in the form an
agent working in this repo reads: the two hypervisor job labels, the verified
metric names, the traps in
["Metric alerts — the media stack"](#metric-alerts--the-media-stack), and the
["Deliberately not monitored"](#deliberately-not-monitored) list, so a
diagnosis does not start by guessing a metric name that has never existed.

## Adding things

### Adding a dashboard

1. Drop a ConfigMap in `clusters/lab/platform/monitoring/` with the
   dashboard JSON under a `*.json` key, labelled **`grafana_dashboard: "1"`**.
   The value matters as much as the key: the chart renders the sidecar with
   `LABEL=grafana_dashboard`, `LABEL_VALUE=1`, `NAMESPACE=ALL`, and a bare
   `grafana_dashboard: ""` is not picked up.
2. List the file in `monitoring/kustomization.yaml` under `resources:`.
   **Not** `configMapGenerator` — that appends a content hash to the name,
   which would break `loki-rules`' mount and is pointless churn here.
3. If the object serialises past ~256 KB, add
   `argocd.argoproj.io/sync-options: ServerSideApply=true` to it. This is a
   real ceiling, not a theoretical one: `dashboard-node-exporter-full.yaml`
   is 2,513 bytes past the 262,144-byte
   `kubectl.kubernetes.io/last-applied-configuration` cap that a client-side
   apply writes, and without the annotation it is rejected outright with
   `metadata.annotations: Too long`.
4. One dashboard per ConfigMap, so one bad JSON blob cannot take another
   dashboard down with it.
5. **Give the data key a name no other dashboard ConfigMap uses.** The
   sidecar writes every key into the one flat `/tmp/dashboards`, so two
   ConfigMaps sharing a key name overwrite each other's file — and
   `lab-overview.json` in particular is named by
   `kube-prometheus-stack.yaml`'s `default_home_dashboard_path`. See
   [The four dashboards](#the-four-dashboards).

Vendor the JSON rather than fetching it at runtime — Argo renders from git
with no network step. Minify it: pretty-printed, dashboard 1860 is 522 KiB
in a block scalar, which trips the pre-commit `check-added-large-files`
guard at 500 KiB.

If the dashboard has a datasource *variable* rather than a hardcoded uid, it
resolves to Grafana's default datasource — which is the provisioned
Prometheus (`isDefault: true`, uid `prometheus`). Provision a second default
and every such dashboard quietly re-points.

### Adding a metric alert rule

1. Check the chart does not already ship it (`kubectl -n monitoring get
   prometheusrules`, or grep the rendered chart). Duplicating an upstream
   alert is the most common way to make alerting worse.
2. Add it to `rules-pve-host.yaml`, `rules-cluster.yaml`, `rules-media.yaml`
   or `rules-backups.yaml`, or a new `PrometheusRule` listed in
   `kustomization.yaml`.
3. **No `release:` label, and any namespace.** Both selector pairs are `{}`;
   see [What gets scraped](#what-gets-scraped).
4. If it touches host metrics, carry the `job="pve-node"` matcher.
5. No angle brackets in annotations (Telegram HTML parse mode).
6. Verify it *evaluates*, not just that it renders: paste the expression
   into Grafana Explore against Prometheus and confirm it returns the series
   you think it does. A rule that matches nothing is indistinguishable from
   a rule that is not firing.

### Adding a log alert rule

1. Add a rule to the existing `lab-logs` group in `loki-rules.yaml`, or a
   new key in the same ConfigMap's `data:` — each key becomes one rule
   *file* under the tenant directory.
2. **The ConfigMap may contain nothing but rule files.** Loki's local rule
   store loads every non-directory entry in the tenant directory, and one
   unparseable file aborts the load of *all* groups. No README key, no
   checksum.
3. `expr` is LogQL and must be a **metric** query (`count_over_time`,
   `rate`, …) reduced to a number. A bare log-stream selector is rejected at
   load time.
4. Use only the labels in the table above.
5. Everything else — `alert`, `for`, `labels`, `annotations` — is the
   Prometheus alerting-rule schema, because the ruler runs the Prometheus
   rule manager.
6. Test the expression in Grafana Explore first. There is no error for a
   selector that matches zero streams.

## Grafana has no authentication of its own

The login form is off, basic auth is off, and `auth.proxy` trusts the
`Remote-User` header. For traffic arriving through the Ingress that is safe:
the annotation routes every request through Authelia's forwardauth
Middleware, and Traefik overwrites the header on the forwarded request from
Authelia's reply, discarding whatever the client sent.

That says nothing about traffic that never reaches Traefik, and the Grafana
Service is a plain ClusterIP. Any pod in the cluster could otherwise run

```sh
curl -H 'Remote-User: whoever' http://kube-prometheus-stack-grafana.monitoring
```

and — `auto_sign_up: true` plus `auto_assign_org_role: Admin` — be minted an
Org Admin on the spot. The neighbours are the `media` namespace: Deluge, the
*arrs, FlareSolverr, all of which exist to parse hostile input from indexers
and trackers.

[`monitoring/networkpolicy-grafana.yaml`](../clusters/lab/platform/monitoring/networkpolicy-grafana.yaml)
closes that half. It selects the Grafana pod and allows ingress on container
port 3000 from exactly two namespaces — `traefik` (real users) and
`monitoring` (Prometheus scraping `/metrics`). Selecting a pod denies
everything else, so that list has to stay complete. Grafana's own
`auth.proxy.whitelist` is not the tool for this: it matches source IPs, and
Traefik shares the flannel pod CIDR with every media pod, so any whitelist
wide enough to admit Traefik admits the attacker too.

**The caveat: a NetworkPolicy only does anything if a controller enforces
it.** k3s ships kube-router's network-policy controller enabled by default,
and this cluster does not disable it — `k3s_disable_components` is
`[traefik]` and nothing else. If `--disable-network-policy` is ever added,
this object becomes a silently inert piece of YAML and Grafana's header trust
becomes cluster-wide, with no error anywhere. Anyone touching that flag owns
this consequence.

Related: `GF_SECURITY_DISABLE_INITIAL_ADMIN_CREATION=true` means there is no
Grafana *server* admin. The first Authelia user through the door is
auto-created as an Org Admin. To get a real server admin back, point
`grafana.admin.existingSecret` at a ksops Secret — do not un-set that
variable, or the subchart mints a fresh random password on every render and
Grafana restarts on every Argo sync.

## Secret rotation

### Telegram — a three-place credential

The bot token and group id now exist in **three** places, and a rotation
that updates fewer than all three leaves something silently unable to
notify:

| Place | What lives there | How to change it |
|---|---|---|
| [`clusters/lab/apps/media-common/telegram.sops.yaml`](../clusters/lab/apps/media-common/telegram.sops.yaml) | Secret `telegram` in `media` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) | `sops clusters/lab/apps/media-common/telegram.sops.yaml` |
| `clusters/lab/platform/monitoring/alertmanager-config.sops.yaml` | `bot_token` and `chat_id` inside the Alertmanager config | `sops clusters/lab/platform/monitoring/alertmanager-config.sops.yaml` |
| Seerr's and Tautulli's own UIs | their notification agents' copies | by hand, in each UI |

That third row is not an oversight to be fixed. Seerr keeps its Telegram
agent in `settings.json` and Tautulli keeps its notification agents in its
own database, not in `config.ini` — neither is templated by this repo, so
neither reads the `media` Secret. That Secret is the single *committed*
home for the credential so a rotation has one place to look, and this table
is the list of places it then has to be carried to.

Rotating:

1. Rotate the token with BotFather (or create the new group and read its id).
2. `sops` both files above. **Keep every value a quoted string** in the
   media Secret — `TELEGRAM_CHAT_ID` is an all-digit negative number, and
   typed unquoted it re-encrypts as `type:int`, which makes the whole Secret
   unappliable at Argo sync time while every other resource in the overlay
   applies fine. CI greps for exactly that.
   In the Alertmanager config the opposite holds *inside* the block scalar:
   `chat_id` must stay a **bare integer**, and the value under
   `alertmanager.yaml` must stay a block scalar (`|`).
3. Update the two UIs.
4. Verify each path independently: Alertmanager via the Watchdog route or
   `amtool`, Seerr by its test-notification button, Tautulli by its own.

### The PVE monitoring token

The exporter authenticates as `monitoring@pve!prometheus`, a
privilege-separation-disabled token inheriting the read-only `PVEAuditor`
ACL that `ansible/roles/pve_permissions` manages. Only the token *value* is
a secret; `PVE_USER` and `PVE_TOKEN_NAME` are plaintext in
`pve-exporter-deployment.yaml`.

The PVE API reveals a token secret exactly once, at creation, so rotation is
remove-then-mint:

```sh
ssh root@pve.lab.tomkatom.com \
  'pveum user token remove monitoring@pve prometheus'      # old value dies here
./scripts/mint-pve-monitoring-token.sh root@pve.lab.tomkatom.com
```

The script refuses to mint over an existing token rather than producing a
`pveum` trace, prints the new value once, and prints the exact sealing
steps. Those are, from the repo root:

```sh
sops clusters/lab/platform/monitoring/pve-token.sops.yaml   # replace the uuid
sops -d clusters/lab/platform/monitoring/pve-token.sops.yaml   # must print it back
grep -c 'type:str]' clusters/lab/platform/monitoring/pve-token.sops.yaml   # must be 1
```

Between the `remove` and the merge of the re-sealed Secret, `pve_up` and
every `pve_*` series is absent and `PveGuestNotRunning` cannot fire. The
exporter's own liveness probe hits `/`, not `/pve`, so the pod stays up and
`up{job="pve-exporter"}` goes to 0 rather than the pod crash-looping.

## The ServerSideApply → skipCrds fallback

`kube-prometheus-stack.yaml` carries `ServerSideApply=true` because the
chart ships 10 CRDs totalling ~4.4 MB, six of them individually past the
262,144-byte `last-applied-configuration` ceiling that a client-side apply
writes (`prometheuses` alone is 830,666 B). Client-side, the API server
rejects the apply and the entire sync fails on the CRDs before a single
workload is created.

If SSA is ever not enough — a CRD that needs to be owned and versioned
separately from the workloads, or an upgrade that fights over field
ownership — the escape hatch is:

1. Set `helm.skipCrds: true` on `kube-prometheus-stack.yaml`.
2. Add a dedicated `prometheus-operator-crds` Application at a **lower sync
   wave**, so the CRDs are established before anything references them.

Deliberately not done today: one Application is simpler to reason about, and
SSA handles it. Note the per-resource form of the same option already exists
in the overlay — `dashboard-node-exporter-full.yaml` carries
`argocd.argoproj.io/sync-options: ServerSideApply=true` on itself, because
only that one object is oversized and switching the whole
`monitoring-config` Application would change how every ksops Secret and CR
in the overlay is applied for the sake of one dashboard.

## Deliberately not monitored

Each of these is a decision, not a gap. Revisit them on purpose.

- **Blackbox / external probes.** There is no `blackbox_exporter` and no
  synthetic HTTP check. Everything here watches the lab *from inside the
  lab*, on the one machine it is watching — so a dead uplink, a broken host
  NAT, or a Cloudflare problem is invisible to it, and so is the alert path
  itself, which leaves by the same wire. A probe is only worth anything from
  somewhere else, and "somewhere else" means a second host or a paid
  service. Until there is one, the honest position is that this stack
  detects *internal* failures only.
- **ZFS scrub staleness.** Nothing alerts on "the last scrub finished too
  long ago". The textfile collector emits pool capacity and health, not a
  last-scrub timestamp, so the rule has no metric to stand on — and scrub
  scheduling is not managed by this repo at all, so the alert would be
  asserting a policy that does not exist. `PveZpoolNotOnline` and
  `SmartDeviceUnhealthy` catch the failures a scrub surfaces. Emit the
  timestamp from `lab-node-metrics.sh` first if this ever matters.
- **Tautulli.** Not scraped. Its Prometheus exporters are unmaintained; the
  live session data they would expose comes from Plex directly; and
  Tautulli's actual value here is the watch-*history* UI, which is not a
  metrics question. It stays a UI.
- **Per-torrent Deluge metrics.** Not enabled: a session of several hundred
  permanently-seeding torrents, times a handful of series each, is a
  cardinality problem in a 15 GiB Prometheus — for data that is one click
  away in the Deluge UI. Aggregates by torrent state are the right
  granularity.
- **`importBlocked` queue items, as an alert.** The condition that motivated
  the media exporters in the first place, and the one thing here that is a
  gap rather than a decision — but the decision *not to fake it* is
  deliberate. exportarr v2.3.0 cannot express it (see the ⚠ under
  [Metric alerts — the media stack](#metric-alerts--the-media-stack)), and
  the two ways to close it are an upstream release, or a probe of the *arr
  queue API that would need a blackbox exporter this lab does not run and an
  API key handed to it. The first is a one-line tag bump plus the restore
  recipe already written into `rules-media.yaml`; wait for it. Meanwhile the
  queue-size panel shows the symptom and `ArrHealthErrors` catches the
  subset Servarr raises as a health issue.
- **The local ZFS snapshot tier.** `ansible/roles/zfs_snapshots` takes
  hourly/daily/weekly sanoid snapshots of `rpool/ROOT/pve-1` and the k3s VM's
  backed-up zvols, and nothing alerts on them — its failure mode is a *stale*
  snapshot set rather than a missing one, and no metric carries a snapshot
  age today. It is the tier whose loss costs least (B2 still holds
  everything, and `ZfsPoolCapacityHigh` already watches the pool they live
  on), but it is named here so that
  [Metric alerts — backups](#metric-alerts--backups) is not read as covering
  it. Closing it means emitting a newest-`autosnap_`-per-dataset timestamp
  from a textfile collector first.
- **Argo CD's own metrics.** Argo self-manages and its sync state is visible
  in its UI; a failed sync surfaces as the *symptom* — a missing or stale
  object — through the rules above. Worth adding the ServiceMonitor when
  there is a specific question it would answer.

## Verification

The checks that can only be run against a live cluster:

```sh
# every Application Synced/Healthy
kubectl -n argocd get applications kube-prometheus-stack loki alloy \
  monitoring-config exportarr plex-exporter deluge

# Prometheus: every target UP, and the hand-written rule groups loaded
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090 &
curl -s localhost:9090/api/v1/targets?state=active \
  | grep -o '"scrapePool":"[^"]*"\|"health":"[^"]*"'
curl -s localhost:9090/api/v1/rules | grep -o '"name":"pve-host"\|"name":"cluster-extra"\|"name":"media"'

# the five media targets specifically — the only ones outside `monitoring`,
# so this is also the check that the empty namespace selectors work
curl -s localhost:9090/api/v1/targets?state=active \
  | grep -o '"job":"\(exportarr-[a-z]*\|plex-exporter\|deluge\)"' | sort -u

# Loki: the ruler actually loaded loki-rules (an empty result means the
# ConfigMap name, the /rules/fake mount path, or the LogQL is wrong)
kubectl -n monitoring port-forward svc/loki 3100:3100 &
curl -s -H 'X-Scope-OrgID: fake' localhost:3100/loki/api/v1/rules

# Alloy is shipping both sources — expect the pod-log labels and the journal
curl -s -G localhost:3100/loki/api/v1/label/job/values
curl -s -G localhost:3100/loki/api/v1/label/namespace/values

# the NetworkPolicy: Grafana must NOT answer a pod in another namespace
kubectl -n media run netpol-probe --rm -i --restart=Never \
  --image=curlimages/curl -- \
  curl -sS --max-time 5 http://kube-prometheus-stack-grafana.monitoring   # must time out

# the home dashboard: grafana.ini's path and the file the sidecar actually
# wrote must be the same string. A mismatch is silent — Grafana just serves
# its built-in home page instead.
kubectl -n monitoring exec deploy/kube-prometheus-stack-grafana -c grafana -- \
  grep -A1 '\[dashboards\]' /etc/grafana/grafana.ini
kubectl -n monitoring exec deploy/kube-prometheus-stack-grafana -c grafana -- \
  ls -l /tmp/dashboards/
```
